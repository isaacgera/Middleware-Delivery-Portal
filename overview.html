Middleware Delivery Portal MDP

Phase 1 — Estimation & Planning. A single source of truth for middleware effort & cost estimates.

MDP replaces the scattered Excel “Menu Cards” used to estimate middleware work with one governed, auditable web app. A team of a few delivery managers and an administrator build Requests (estimates) for IBM MQ, Oracle WebLogic, Axway CFT and WildFly — pulling service figures from an approved, version-controlled Menu Card, and producing clean customer-ready PDFs. Every figure is traceable, every change is logged, and the numbers can’t drift because each line snapshots the Menu Card value at the moment it’s added.

What it does

Versioned Menu Cards

Import the approved Menu Card workbook; exactly one version is Active at a time. Older versions are archived, never lost.

Product Catalogue

Browse the active card’s services by component and size, with search and a detail view of every figure.

Requests & line items

Build an estimate from catalogue services, scoped to its component + size, with live totals as you go.

Deterministic costing

No guesswork: a line is its snapshot × quantity, totals are the sum. Money is exact (no rounding drift).

Status workflow

New → Pending → Approved → In Progress → Done, plus Archive and Cancel. Any status, any time, with guards where they matter.

Customer PDFs

Generate a clean, branded estimate PDF per request — download on desktop, share on mobile.

Dashboards

Volume, value and breakdowns by product / CFU / size / customer, with filters and charts.

Flow analytics

Throughput, cycle time, aging and an honest run-rate projection — reconstructed from real history.

Full audit trail

Every login, import, create, change, delete and export is recorded — append-only and tamper-evident.

Who uses it

  • Delivery Managers — create and manage requests, browse the catalogue, generate PDFs, view dashboards & their own history.
  • Administrators — everything a Delivery Manager can do, plus importing/activating Menu Cards and seeing the full audit log across all users.

How it’s built

  • Server-backed, multi-user (3–5 concurrent) with a real relational database — a single source of truth, not a per-person spreadsheet.
  • Role-based access with secure sessions and hashed passwords; an Entra ID sign-in seam is planned.
  • Local-first & private — data stays on the BT server; nothing is sent to any third party.
  • Dependency-free — runs on the Node.js runtime alone, suiting a locked-down environment; light/dark themes and keyboard/screen-reader accessibility built in.
